pt-pay 技术架构、部署结构与 New API 的关系

pt-pay 是挂在 New API 旁边的独立服务：负责微信扫码充值、退款、会员资格和邀请奖励，New API 本身一行代码不改。本页按「和 New API 的边界 → 架构 → 部署 → 各条调用链 → 数据 → 运维」的顺序展开。

01 · 边界

与原 New API 的关系：旁挂、单向依赖、零改动

New API 仍是用户、登录、额度和计费的唯一权威。pt-pay 不直接读写 New API 的数据库，只通过 New API 自己的 HTTP 接口交互：用用户的 access token 核实身份，用root 的系统访问令牌（PAT）调管理接口加减额度。反方向 New API 对 pt-pay 完全无感知，唯一的接缝是后台「充值链接」指向 /pay/。

沿用 New API 的

  • 登录态：页面同源调用 /api/user/auth/refresh 换 access token，pt-pay 再用 /api/user/self 核实，不另设账号体系
  • 额度体系：入账/扣回都走 /api/user/manage，由 New API 自己同步 Redis 缓存并写充值日志
  • 邀请关系：注册时的 aff 码 → 用户的 inviter_id，pt-pay 只读
  • 汇率：/api/status 的 usd_exchange_rate（7.3）与 quota_per_unit（500000）
  • 运维门禁：/ops/* 复用站点现有的 auth_request /_ops_check

pt-pay 自己负责的

  • 充值订单、微信下单/回调/查单/关单、每日账单核对
  • 退款（先扣回余额再原路退款）及失败补偿
  • 正式会员判定、邀请资格、风控、奖励发放/收回
  • 赠送余额批次（180 天有效期）的消耗跟踪与到期扣减
  • 自己的数据：new-api-postgres 里的独立库 ptpay（独立角色，看不到 New API 的表）

为什么不用 New API 自带功能

  • 自带易支付充值按整美元入账（amount × QuotaPerUnit），本站汇率 7.3，最小单位 7.3 元，做不出「10 元档、1 元 = 1 元」。pt-pay 自算额度：元 ÷ 汇率 × quota_per_unit
  • 自带邀请奖励注册即发、无会员门槛和风控。上线时把 QuotaForInviter/Invitee 改为 0，由 pt-pay 接管
  • 数据库：复用 New API 的 PG 16 实例，但用独立角色 + 独立库（同 sub2api 先例）。New API 升级做数据库迁移互不影响，权限隔离，备份可单独做

pt-pay 调用的 New API 接口一览

02 · 逻辑架构

技术架构图

所有外部流量都经过 nginx。pt-pay 内部分三层：入口层处理 HTTP 和定时任务，业务层是充值与会员两个引擎，适配层封装对 New API 和微信的调用。两个模块共用 PostgreSQL 里的 ptpay 库，会员模块只写自己的表，对 orders/refunds 只读。

用户/运维流量 pt-pay → New API（本机回环 HTTP） 与微信支付之间 pt-pay → PostgreSQL（独立库 ptpay） 三行由上到下：入口层 → 业务层 → 适配层 → 存储

04 · 调用链

充值链路：从扫码到到账

用户在 New API 钱包页点充值链接进入 /pay/。收银台和 New API 同域，浏览器带着 New API 的 cookie 就能换到 access token，所以用户无需再次登录。下图省略了 nginx 转发这一跳。

sequenceDiagram

  participant U as 浏览器 / 微信
  participant A as New API
  participant P as pt-pay
  participant W as 微信支付
  U->>A: POST /api/user/auth/refresh（同源 cookie）
  A-->>U: access_token + user.id
  U->>P: POST /pay/api/orders {yuan}（Bearer + New-Api-User）
  P->>A: GET /api/user/self（核实身份）
  P->>A: GET /api/status（汇率、quota_per_unit）
  P->>P: 校验 10–5000 整元、未支付单不超过 5 笔，落库 created（额度已算好）
  P->>W: Native 下单（time_expire = 30 分钟）
  W-->>P: code_url
  P-->>U: 二维码 SVG
  U->>W: 手机扫码付款
  W->>P: POST /pay/api/wechat/notify
  P->>P: 序列号与 ±300s 时间戳 → 验签解密 → 核对商户号、AppID、金额
  P->>P: created/closed → paid，再条件 UPDATE 抢 paid → crediting
  P->>A: POST /api/user/manage add_quota（管理员 PAT）
  A-->>P: success
  P->>P: crediting → credited
  P-->>W: 200 SUCCESS
  loop 每 2 秒，最长 30 分钟
    U->>P: GET /pay/api/orders/{no}
  end

stateDiagram-v2
  direction LR
  [*] --> created: 下单
  created --> paid: 回调或查单 SUCCESS
  created --> closed: 超过 35 分钟关单
  closed --> paid: 关单后迟到的成功

  credited --> [*]

订单状态机的实现逻辑

  • 只加一次：回调和每分钟的 reconcile 会同时尝试入账，但只有一方能执行成功 UPDATE … SET status='crediting' WHERE status='paid'，另一方直接退出。
  • New API 明确拒绝（CreditRejected）：退回 paid，下一轮自动重试。
  • 结果未知（超时或 5xx，CreditUnknown）：停在 crediting，不自动重试以免重复入账。超过 5 分钟报卡单，由人工执行 credit-check 查 New API 充值日志，再用 credit-resolve 定论。
  • mismatch 是终态：金额、商户号或 AppID 与订单不符，只记日志并给微信回 200，不自动处理。
  • 回调里非 TRANSACTION.SUCCESS 的事件（例如退款通知）直接回 200 忽略。
05 · 兜底

补单对账：reconcile 每分钟与 bill 每日

pt-pay reconcile（每 60 秒）

  1. created 且超过 60 秒的订单去微信查单：已付款的补入账；超过 35 分钟的关单。关单失败会再查一次，绝不关闭已付款的订单。
  2. 停在 paid 的订单重试入账。
  3. 每 10 分钟回查 24 小时内关闭的订单，迟到的付款成功照样入账。
  4. 把 crediting 超过 5 分钟的卡单和 mismatch 订单列进报告。
  5. submitted 状态的退款去微信查结果，转为 succeeded 或 failed。
  6. 把 failed 退款，以及卡住超过 5 分钟的 pending/debited/restoring、debit_unknown、restore_unknown 列进报告。

每笔订单单独 try/except，一笔出错不影响其它笔。遇到 AdminAuthFailed（PAT 失效）则本轮停止所有加减额度操作，只告警一次。

pt-pay bill（每天 10:30）

调用微信交易账单接口，下载昨天的账单（支持 gzip），与本地当天的已付款订单逐笔比对。有差异时退出码为 1，结果写到 /ops/bill/。

退出码组合：bill 失败优先返回 bill 的退出码；bill 成功但页面写入失败，返回写页面的退出码，避免页面静默过期而任务仍显示成功。

时间与重试参数

  • 二维码有效期 30 分钟；本地关单 35 分钟（晚于二维码过期，避免提前关单）
  • 每用户最多 5 笔未支付订单
  • crediting 超过 5 分钟算卡单
06 · 调用链

退款链路：先扣回余额，再原路退款

退款只能由运维通过 pt-pay-admin refund <订单> <元> <操作人> 发起。先扣回余额，是为了防止用户把充值额度花掉之后钱又退回去。扣回前会检查用户当前余额；余额查询失败时拒绝退款，确认无误后需加 --force 才能继续。同一订单同一时间只允许一笔退款在途。

stateDiagram-v2
  [*] --> pending: 预占 refunded_fen
  pending --> released: New API 拒绝扣回
  pending --> debit_unknown: 扣回结果未知
  pending --> debited: subtract_quota 成功
  debited --> submitted: 提交微信退款
  submitted --> succeeded: 微信 SUCCESS
  submitted --> failed: CLOSED 或 ABNORMAL
  failed --> restoring: refund-restore
  restoring --> restored: add_quota 加回
  restoring --> restore_unknown: 结果未知
  restore_unknown --> restored: refund-restore-resolve

各状态的处理方式

  • debited 卡住：余额已扣回但提交微信失败，用 refund-retry 以同一退款单号重新提交（微信按 out_refund_no 幂等）。
  • failed：微信没有退成，用 refund-restore 把扣回的额度加回给用户。
  • *_unknown：可能已经扣回或加回，冻结等待人工核对后定论。
  • 用户在「我的充值记录」里看到的已退金额只统计 debited、submitted、succeeded 三种状态，不包括 failed 和补偿中的退款。
  • 会员模块只认 succeeded：退款还在途中时不收回奖励。如果收回后微信又判定退款失败，奖励就再也补不回来了。
07 · 调用链

会员与邀请奖励：member-run 每分钟一轮

会员模块没有自己的写入接口，全部逻辑都在定时任务里：从 New API 拉新注册用户建立邀请关系，从本地订单表判断资格，再通过 New API 管理接口发放和收回奖励。页面只负责展示。

规则（member/rules.py）

  • 正式会员：至少有一笔已入账的充值，实付金额减去已成功退款后仍 ≥ 10 元
  • 有效邀请：被邀请人注册后 30 天内完成上述首充，且邀请人届时已是正式会员
  • 奖励：邀请人、被邀请人各得 10 元赠送余额，有效期 180 天
  • 排除：分组为 vip / svip / superall / bileego 的用户，以及已禁用的用户
  • 预算：每月 2000 元，超过即转人工审核
  • 审核超时：7 天未处理自动驳回

风控（member/risk.py）

  • same_payer：双方付款用的微信 openid 有交集
  • shared_ip：双方下单时的 client_ip 有交集（New API 日志不记录 IP，所以用订单 IP 代替）
  • disposable_email：被邀请人使用一次性邮箱
  • monthly_cap：邀请人本月已获奖 20 次
  • budget：本月发放金额加上本次将超过 2000 元
  • daily_alert：邀请人当天超过 5 次，只告警，不拦截

除 daily_alert 外，命中任意一项都转人工审核（review）。

运行前置（fail-closed）

  • 拿到文件锁，否则说明上一轮还在跑，直接跳过
  • 必须已执行 member-init-watermark，避免把历史邀请关系全部回填导致误发奖
  • 必须设置 PT_MEMBER_PILOT（灰度名单）或 PT_MEMBER_FULL_LAUNCH=1，两者都没设置就拒绝运行
  • member-pause 后跳过本轮

一轮 run() 的 9 个步骤

  1. 同步邀请关系：从水位往回退 10 秒拉 New API 新用户，把带 inviter_id 的写成 registered。水位只推进到已确认安全的位置，处理失败的记录下一轮会重试。
  2. 资格判定：registered 状态的关系去本地 orders 表找被邀请人 30 天内的合格首充；不在灰度名单、属于排除分组、账号被禁用或邀请人不是会员的，标为 ineligible。
  3. 风控与发奖：qualified 状态的关系再核一次邀请人是否仍是会员，然后做风控判定。未命中的转为 rewarding，给双方各写一条 grant 流水。
  4. 收尾与自愈：rewarding 状态下若有流水缺失或 pending 卡住，按同一幂等键补发；两条流水都 applied 后建立赠送批次，转为 rewarded。
  5. 审核超时：review 状态超过 7 天转为 rejected。
  6. 收回：触发订单成功退款后实付低于 10 元的，转为 clawing，双方各扣回未过期的部分。若批次还有未定论的过期扣减，先等人工处理，避免重复扣。
  7. 赠送余额：读 New API 的 used_quota 增量，按发放先后抵扣未过期批次（先扣赠送）；到期批次按「剩余额度与当前余额取较小值」扣减。
  8. 汇总流水异常：统计状态为 unknown 和 rejected 的流水。
  9. 卡单检查：rewarding/clawing 超过 10 分钟仍未完成的，以及到期超过 10 分钟仍未扣减的赠送批次，列入报告。
stateDiagram-v2
  [*] --> registered: 同步到带 inviter_id 的新用户
  registered --> expired: 30 天内无合格首充
  registered --> ineligible: 非灰度 / 排除分组 / 禁用 / 邀请人非会员
  registered --> qualified: 首充 ≥ 10 元已入账
  qualified --> ineligible: 邀请人已失去会员资格
  qualified --> review: 命中阻断风控
  qualified --> rewarding: 风控通过
  review --> rewarding: member-approve
  review --> rejected: member-reject 或 7 天超时
  rewarding --> rewarded: 双方 grant 均 applied
  rewarded --> clawing: 退款后实付低于 10 元
  clawing --> clawed_back: 双方 clawback 均 applied

奖励流水 Ledger：怎么保证不多发、不漏发

  • 每次加减余额前先插入一条 reward_ledger，状态为 pending，idem_key 设唯一约束：
    ref{id}:invitee · ref{id}:inviter
    ref{id}:invitee:claw · ref{id}:inviter:claw
    lot{id}:expire
  • 插入成功后才调用 New API，结果写回 applied / rejected / unknown
  • 幂等键冲突说明已经做过，直接返回原结果；pending 超过 5 分钟按 unknown 处理
  • rejected：确定没加，用 member-retry 重试
  • unknown：可能已加，属于 P0；人工到 New API 核对后用 member-resolve 定论

referrals会员inviter_id、invitee_id（唯一）、status、trigger_order、risk_hits、reviewed_by一个被邀请人只对应一条邀请关系
reward_ledger会员user_id、quota、kind（grant/clawback/expire）、idem_key（唯一）、status所有对 New API 余额的改动都记在这里
gift_lots会员user_id、quota、remaining、expires_at、ledger_id（唯一）、expired赠送余额按批次管理，180 天到期
member_meta会员key / valueusers_watermark、paused、used:{uid} 基线

表结构在 pt_pay/migrations/001_init.sql，时间戳、金额、额度一律 bigint。隔离级别用默认的 READ COMMITTED：单条条件 UPDATE 天然只有一方抢到；退款预占/释放/补偿和赠送批次扣减用事务 + FOR UPDATE 行锁，锁顺序固定（先退款单后订单），等锁超过 5 秒提示「数据库繁忙，请重试」。

  • /ops/bill/：每天刷新，展示微信账单与本地的差异

会员命令

member-init-watermark · member-reviews · member-approve · member-reject · member-retry · member-resolve · member-show · member-pause · member-resume

P0 告警

  • ledger_unknown：奖励流水结果未知
  • rewarding_stuck：发放或收回卡住超过 10 分钟
  • gift_expiry_stuck：赠送余额到期后未能扣减
  • 充值侧：crediting 卡单、mismatch、AdminAuthFailed、各类 refund unknown
给用户办理退款前，先清完该用户所有 unknown 和 rejected 流水。

安全要点

  • 微信商户密钥和 New API PAT 只放在 /etc/pt-pay/，权限 640
  • 8098 端口只监听 127.0.0.1；nginx 覆写 XFF 头，服务端取最右侧地址
  • 回调先检查序列号和时间戳再验签，防止伪造序列号让 SDK 去拉证书（DoS）
  • 日志只记订单号、交易号和金额，不记 openid 和回调原文
  • systemd：ProtectSystem=strict、NoNewPrivileges，只有运维页目录可写
  • 数据库角色 ptpay 只拥有自己的库，碰不到 New API 的数据
