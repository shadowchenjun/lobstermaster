LiteLLM

在不改 New API 一行代码的前提下，把 LiteLLM 的治理、可观测和内容护栏叠加上去：New API 继续管「卖」（用户、额度、充值、定价），LiteLLM 专门管「控」（上游 key 池、成本预算、护栏、指标）。本文是方案；落地步骤、验证清单和配置草稿见配套文档《PoC 验证清单与配置草稿》。

适用 Perfectoken 杭州机（New API rc.37 + pt-pay） 依据 New API main 分支源码、LiteLLM 1.103.0 文档与本地实测 方案草稿本地预检已通过待真实环境 PoC
原则目标架构职责划分身份映射治理可观测内容护栏分阶段路线风险与代价部署形态
01 · 原则

三条不动摇的约束

计费只有一个来源

用户余额、扣费、退款只在 New API 里发生。LiteLLM 记录的是上游成本，只用来设上限和做毛利分析，从不直接影响用户余额。

不改 New API 源码

New API 仍在 RC 阶段、迭代频繁，而且是 AGPL 许可。所有能力通过「渠道指向 LiteLLM」接入，和 pt-pay 外挂支付的思路一致。

随时可以回滚

每个分组保留一条平时禁用的直连渠道。LiteLLM 出问题时，在 New API 后台禁用 LiteLLM 渠道、启用直连渠道即可恢复，不需要发版。

02 · 目标架构

前台卖、后台控

LiteLLM 以容器形式加入现有的 newapi-net 网络。这和 New API 已经通过 http://sub2api:8080 串联 sub2api 是同一种做法，所以不需要新的网络改造。

04 · 身份映射

LiteLLM 能看到多细：分组级，而不是用户级

New API 转发给上游时，能不能把「当前是哪个用户」带过去，决定了 LiteLLM 能做多细的治理。查 New API main 分支源码的结论如下。

New API 机制能做什么能否带用户 ID
渠道「请求头覆盖」只支持两种占位符：{api_key}（渠道密钥）和 {client_header:名称}（客户端传来的请求头）否
渠道「参数覆盖」上下文里有 user_id、user_group、using_group，但只能用在条件判断里；set、set_header 写入的值是静态的否（只能按分组写固定值）
客户端自带 user 字段会原样透传，但由客户端自己填写，不可信不可用于治理
结论：按分组映射。New API 每个分组配一组指向 LiteLLM 的渠道，每组用该分组专属的 team key。LiteLLM 里的预算、限流和指标都是分组粒度。按用户的分析继续用 New API 日志；如果以后确实需要用户级，需要给 New API 提 PR，让参数覆盖支持把上下文变量写成值，这不在本方案范围内。
New API 分组LiteLLM team月度上游成本上限（示例）护栏用途
pocnewapi-poc$5全开（含内容安全）内部测试用户，PoC 和每次升级回归
defaultnewapi-default$300日志脱敏 + 关键词 + 内容安全普通用户
vipnewapi-vip$600同上会员 / 企业客户

预算数字只是占位，需按各分组实际的月消耗乘以 1.5–2 倍设定，作为「失控时的上限」，而不是日常配额。开源版里护栏是全局生效的（default_on），不能按 team 设置不同强度；按 key 或 team 单独配置护栏需要企业版。

05 · 治理

错误码怎么在两个网关之间传递

串联以后，LiteLLM 返回的状态码直接决定 New API 是重试、停止还是禁用渠道。New API 的默认规则见源码 setting/operation_setting/status_code_ranges.go：自动重试的范围是 100–199、300–399、401–407、409–499、500–503、505–523、525–599，504 和 524 永不重试，401 会自动禁用渠道，失败请求会退回预扣的额度。

LiteLLM 返回New API 的行为处理
护栏拦截：400不重试，失败并退回预扣额度理想情况。内置内容过滤和我们写的自定义护栏都返回 400（本地已实测）
自定义护栏抛普通异常：500重试，可能换到别的渠道危险：可能重试到直连渠道，绕过护栏。自定义护栏必须显式抛 HTTPException(400)，草稿已按此实现
Team 预算用完：429重试，同分组其它渠道也是同一个 team key，同样 429，次数用完后失败本地实测 1.103.0 写死为 429，文档里的 422 和返回码开关在这个版本不成立。代价是几次无效重试；前提是该分组没有启用的直连渠道
上游限流：429重试LiteLLM 内部已经在 key 池之间重试过，再由 New API 兜底一次也合理
LiteLLM 虚拟 key 失效：401自动禁用该渠道轮换 key 时要先改 New API 渠道再吊销旧 key，否则渠道会被自动禁用
LiteLLM 宕机：连接失败或 502/503重试，同组渠道全部失败启用直连渠道回滚；LiteLLM 健康检查纳入告警

预算熔断为什么值得做

卖额度的生意里，最怕的是「收入按倍率算，成本没有上限」：倍率配错、某个渠道被盗刷、某个模型突然涨价，都会在用户正常付费的情况下持续亏损，而 New API 本身察觉不到。LiteLLM 的 team 预算按真实上游成本封顶，触发时这个分组暂时不可用。这虽然影响体验，但把最大亏损锁定在一个已知数字内。

06 · 可观测

三层视角，按成本从低到高

层次看什么怎么做
业务（New API）每个用户、令牌、模型的消费和收入，渠道错误率现有日志 + 控制台；可以用 LOG_SQL_DSN 把日志拆到独立库，再接 Grafana
技术（LiteLLM）每个分组、上游 key 的请求量、失败数（带状态码）、延迟、token、花费开源版内置 Prometheus，路径是 /metrics/（注意结尾的斜杠，本地已实测）；Prometheus 加 Grafana 约 200MB 内存
链路（暂不做）单次请求的完整提示词与回复、评估Langfuse 自建需要 ClickHouse 等组件，资源不够；Langfuse Cloud 会把用户对话传到境外，有合规问题

LiteLLM 配置里打开了 turn_off_message_logging，不把提示词和回复内容送进日志回调，只记元数据。

07 · 内容护栏

三层护栏，各管一件事

护栏实现模式说明
个人信息日志脱敏内置 litellm_content_filter，正则匹配手机号、身份证、邮箱logging_only只在日志里打码，不改写发给模型的内容。卖 API 时改写用户真实请求会破坏正常用途
业务禁词内置 litellm_content_filter + 词表文件pre_call 拦截只放少量明确的业务禁词。本地实测：命中时会把关键词和 description 原样返回给用户，词表会被逐条试探出来，所以敏感词库不放在这里
内容安全自定义护栏 cn_guardrail.py → 适配服务 → 阿里云内容安全或网易易盾pre_call 拦截用于履行生成式 AI 服务的内容安全义务。服务不可用时默认拦截（合规优先，本地已实测返回 400），也可以配置为放行
流式输出的限制：post_call 护栏在流式响应时，要等全部内容发给用户之后才运行，只能审计，拦不住。如果需要拦截输出，要用逐块处理的钩子，这会增加首字延迟。所以第一阶段只检查输入；输出的检查先做抽检审计。
08 · 分阶段路线

每一步都可以回退

阶段做什么进入下一阶段的条件回滚方式
0 · 只加观测New API 日志接 Grafana，看渠道错误率、各模型消耗；不改动请求链路有了基线数据：各分组月消耗、渠道 P95 延迟无需回滚
1 · PoC部署 LiteLLM，新建 poc 分组和内部测试用户，跑完 PoC 清单清单全部通过，尤其是流式计费一致、拦截后退额度删除 poc 分组渠道
2 · 灰度选一个分组（例如 vip）切到 LiteLLM，同时保留禁用的直连渠道；只开日志脱敏和关键词护栏运行 2 周：计费零差异，延迟增加在可接受范围，内存稳定启用直连渠道，禁用 LiteLLM 渠道
3 · 全量 + 内容安全所有分组切换；接入内容安全服务，打开 cn-content-safety误拦率可接受；内容安全接口 P95 在 300ms 以内同上；或单独关闭某个护栏
4 · 成本熔断按阶段 0 的基线给每个 team 设预算，接上告警—调高预算或删除预算
09 · 风险与代价

要接受的东西

性能与资源

  • 多一跳本机转发，官方数据是 1k RPS 下 P95 增加约 8ms；内容安全接口另加一次外部调用（预计 50–300ms）
  • 杭州机部署 sub2api 时可用内存约 1.3G，LiteLLM 单 worker 需要预留 700M–1G；不够就需要升级配置，或者放到另一台机器
  • LiteLLM 成为单点：它挂了，同组渠道全部失败

维护与安全

  • LiteLLM 大约每周一个 minor 版本，只维护最近 4 条；必须锁定带 -stable 的镜像并校验 cosign 签名（2026-03 发生过 PyPI 投毒）
  • 实测发现文档和代码对不上（预算返回码），每次升级都要重跑 PoC 清单
  • 上游 key 集中到 LiteLLM，它的 litellm.env 和 master key 是新的高价值目标

功能边界

  • 按 key 或 team 单独配置护栏、按 team 分流日志、Llama Guard 等内置审核回调，都需要企业版
  • 只能做到分组级治理，用户级看不到
  • 两套系统的 token 计数如果不一致，会出现对账差异；流式 usage 必须实测
10 · 部署形态

放在哪、连什么

项目选择
运行方式Docker 容器 litellm，加入 newapi-net；端口只绑定 127.0.0.1:4000，管理 UI 走 SSH 隧道访问
数据库new-api-postgres 里的独立角色和独立库 litellm，和 ptpay、sub2api 同一种模式；表结构由 LiteLLM 启动时的 Prisma 迁移创建
Redis单实例不需要。不要和 New API 共用 Redis：那个实例配置了 allkeys-lru，内存满时会淘汰 key，LiteLLM 的限流计数会被冲掉
New API 渠道OpenAI 模型用「OpenAI」类型，Base URL 填 http://litellm:4000。不能用「自定义」类型：源码中只有 OpenAI 等少数类型会强制带 stream_options.include_usage，否则流式请求拿不到 usage，New API 只能自己估算 token。Claude 模型用「Anthropic Claude」类型，避免两次协议转换
镜像ghcr.io/berriai/litellm:<vX.Y.Z-stable>，写死具体版本并校验签名，不用 latest 或 main

配套文件都在本目录的 litellm/ 和 poc/ 下；逐步操作和验证见《02-PoC验证清单与配置草稿.html》。
