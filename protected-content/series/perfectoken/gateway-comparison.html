01 · 一页结论

不是谁更强，而是钱往哪个方向流

LiteLLM：内部治理型网关 + Python SDK

钱是花出去的：统计每个团队、每个 key 花了多少，给它设预算、限流、护栏。

  • 厂商覆盖最广（README 列 107 项），新模型通常当天可用
  • 可观测生态最完整：Langfuse、Langsmith、Datadog、Prometheus 等
  • 唯一同时提供 Python SDK、MCP 网关和 A2A Agent 网关的一方
  • MIT 许可，可闭源二次开发；但 SSO（超过 5 人）、审计日志、组织级 RBAC 要买企业版

New API：对外分发 / 计费型网关

钱是收进来的：用户注册、充值、兑换码、分组倍率、订阅套餐，按额度扣费。

  • 自带完整的用户与计费体系，这是 LiteLLM 没有的一整层
  • OpenAI / Claude / Gemini 四种协议互相转换，中文客户端生态适配最好
  • Go 单体，资源占用低，SQLite 即可起步
  • AGPL-3.0 加署名附加条款；1.0 仍处于 RC 阶段，插件系统官方标注「不推荐生产」

一句话：如果要向外部用户卖 API 额度，选 New API，因为同类产品里只有它自带这层计费。如果是公司内部统一接入模型、按团队管成本和合规，选 LiteLLM。两者也可以串联：LiteLLM 做内部治理，New API 做对外分发，互为 OpenAI 兼容的上下游。

03 · 定位差异

同叫网关，服务的是两种人

最核心的差别在「谁在网关后面、谁在网关前面」。LiteLLM 前面坐的是公司内部的开发者和团队，它回答「谁花了多少、能不能再花」；New API 前面坐的是外部注册用户，它回答「这个人还剩多少额度、该扣多少」。

LiteLLM 的数据模型

  • Organization → Team → Internal User → Virtual Key 四层（Organization 与组织管理员属于企业版）
  • 花费（spend）是结果：按内置的模型价格表算出每次调用的美元成本，并按 key、team、tag 汇总
  • 没有「用户余额」「充值」「售价」的概念，预算是上限，不是可购买的商品

New API 的数据模型

  • 用户 → 分组 → 令牌；用户有额度余额，令牌可限定可用模型和额度
  • 额度（quota）是商品：模型倍率、补全倍率、分组倍率、缓存倍率共同决定扣费，新版支持计费表达式（阶梯、按次、按时段）
  • 入账途径包括易支付等在线充值、兑换码、邀请奖励、订阅套餐，以及管理员直接调整额度

06 · 许可与风险

许可证义务与安全事件

LiteLLM · MIT + 企业目录

  • enterprise/ 以外的代码是 MIT：可以闭源修改、打包转售，没有开源义务
  • 企业功能由 LITELLM_LICENSE 许可证密钥解锁，价格按部署规模报价，可通过 AWS、Azure Marketplace 采购
  • 企业版支持：工作日工作时间内的专属 Slack 频道；7×24 SLA 另外收费（Sev0 1 小时响应）

New API · AGPL-3.0 + 附加条款

  • 网络条款：修改后通过网络向用户提供服务，必须向这些用户公开修改后的源码
  • 附加署名：修改版必须在界面的关于、页脚等显著位置保留 “Frontend design and development by New API contributors.” 及原项目链接
  • 不接受 AGPL 的组织可以邮件联系 support@quantumnous.com 购买商业授权
  • 通过 HTTP 调用 New API 的独立服务（例如 pt-pay）不属于修改 New API 本身

安全事件与供应链

  • LiteLLM · 2026-03-24：Trivy 依赖被攻破导致 PyPI 发布令牌泄露，litellm 1.82.7 和 1.82.8 被植入窃密木马（PYSEC-2026-2）。import 时即执行，窃取 SSH 密钥、云凭证、K8s token 等，并装 systemd 后门。PyPI 一度隔离该包
  • 此后 LiteLLM 的 Docker 镜像全部使用 cosign 签名，并在 README 给出校验方法
  • New API：本次调研范围内未检索到同级别的供应链事件，但项目迭代快、RC 版本多，同样应当锁定版本号
通用建议：两者都会拿到所有上游厂商的 API Key，是高价值攻击目标。生产环境应锁定具体版本，不跟 latest；对镜像做签名或摘要校验；网关进程只放必要的环境变量；升级前先在测试实例上验证。
07 · 各自擅长

优势与短板

LiteLLM 擅长

  • 企业内部 AI 平台：几百个开发者、几十个团队共用一套模型入口，按团队分摊成本、设预算
  • 多云与合规：Bedrock、Vertex、Azure 私有部署统一接入，满足数据不出云的要求
  • 可观测与评估：请求直接进入 Langfuse、Datadog，便于做 prompt 评估和成本分析
  • 应用代码层：Python 项目直接 import litellm，无需部署任何服务
  • Agent 基础设施：MCP 工具网关、A2A Agent 网关、护栏
  • 基础设施即代码：官方 Terraform、Helm，适合有 SRE 的团队

LiteLLM 短板

  • 不能向终端用户收费，做 API 分发需要自己写整套余额与充值系统
  • SSO（超过 5 人）、审计日志、组织层级、密钥管理服务集成等企业刚需都在付费版
  • Python 栈内存与 CPU 开销较大，大规模时需要调优；Rust 核心仍是 Beta
  • 版本更新极快，issue 积压多，需要紧跟 stable 线；有过 PyPI 投毒事件
  • 控制台只有英文，面向中文运营人员不友好

New API 擅长

  • API 分发与转售：注册、充值、兑换码、邀请、订阅、分组定价一站式，开箱即可对外运营
  • 精细计价：模型、补全、分组、缓存多种倍率，加计费表达式，可按条件、按次、按时段定价
  • 协议互转：让 Claude Code、Gemini CLI、Codex 等客户端用任意上游，是中文 AI 编码工具圈的事实标准
  • 多媒体任务：Midjourney、Suno、视频生成、图片任务统一提交、查询和计费
  • 轻量：Go 单体，SQLite 起步，小机器即可跑；中文控制台与中文社区资料丰富

New API 短板

  • 1.0 仍在 RC，插件系统官方标注「不推荐生产」，升级要谨慎
  • 可观测以内置日志为主，缺少与 Langfuse、Datadog 等工具的原生集成
  • 没有 MCP 或 A2A 网关、没有 Python SDK、没有面向企业合规的审计与 SAML
  • AGPL 加署名条款：修改后对外服务必须开源并保留署名
  • 内置充值有局限（见下一节），日志不记录调用 IP，风控需要外部补充

09 · 落到我们自己

对 Perfectoken 的建议

Perfectoken（api.perfectoken.com.cn）的业务是对外售卖 API 额度，现有架构是 New API rc.37 加自研的 pt-pay 支付与会员服务。以下结合这段时间的实际开发经验给出判断。

继续用 New API 做主网关（结论不变）

  • 用户、额度、分组倍率、邀请码这一层 LiteLLM 完全没有，换掉的成本等于重写整个运营系统
  • pt-pay 只通过 HTTP 管理接口与 New API 交互，没有修改 New API 源码，所以不触发 AGPL 的源码公开义务；如果以后要改 New API 前端，需要保留署名
  • New API 管理接口（/api/user/manage 调整额度、/api/user/ 查询用户、/api/status 查汇率）足够支撑外挂业务服务

已踩到、需要记住的 New API 局限

  • 内置易支付按整美元入账：到账额度 = 金额 × QuotaPerUnit，本站汇率 7.3，最小充值单位约 7.3 元，做不出「10 元档、1 元 = 1 元」，所以另写了 pt-pay
  • 调用日志不记录 IP（rc.37 实测 0/1783 条），邀请风控只能改用 pt-pay 订单里记录的 IP
  • 内置邀请奖励注册即发、没有门槛，上线会员体系时要把 QuotaForInviter 和 QuotaForInvitee 改为 0
  • rc.38 起的版本仍标注「不推荐生产」，建议停留在 rc.37，等 1.0 正式版或插件系统转正后，先在测试实例验证再升级

LiteLLM 可以在哪里帮上忙

  • 暂不需要：当前规模下，New API 自带的日志和看板够用，再加一层会多一跳延迟和一套运维
  • 值得引入的时机：上游渠道很多、需要按上游做成本和延迟分析，或者要给内部团队（例如清竞智能的项目）单独开放模型并做成本核算时，可以把 LiteLLM 挂在 New API 后面作为一个渠道，或单独给内部使用
  • 引入时锁定 -stable 镜像并校验 cosign 签名，不要用 pip 安装的 latest 版本
