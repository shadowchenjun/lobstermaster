> **我们的后续发布约定：先检查，再预览验收；使用生产配置构建后再次验收，最后把已验证的版本切换到正式域名。**

<h2 id="flow">一、发布流程全景</h2>

```text
开发分支 / PR
    ↓
类型检查 + 单元测试 + 后端测试 + 构建
    ↓
Vercel Preview → 页面、API 与业务流程验收
    ↓
检查通过后合并生产分支
    ↓
使用 Production 配置构建暂存生产部署
    ↓
在独立部署 URL 验收，正式域名继续服务旧版本
    ↓
Promote 已验收版本，正式域名切换
    ↓
正式环境冒烟检查、日志观察与发布记录
```

每个阶段都要有结果。构建通过说明代码可以生成部署产物；页面能打开说明入口可访问；登录、查询、权限和数据展示正确才说明相关业务经过验收。

<h2 id="roles">二、GitHub 与 Vercel 的分工</h2>

| 环节 | 主要负责方 | 需要明确配置 |
| --- | --- | --- |
| 源码与评审 | GitHub | 分支、PR、审查规则 |
| 自动检查 | GitHub Actions 或其他 CI | 检查命令、触发条件、失败处理 |
| 阻止不合格合并 | GitHub 分支保护 / Rulesets | 必需状态检查与适用范围 |
| 构建与预览 | Vercel | 根目录、构建命令、环境变量 |
| 预览后的业务测试 | 浏览器测试工具或人工 | 真实测试用例与验收标准 |
| 正式流量切换 | Vercel | 暂存生产部署、Checks 或受控发布步骤 |

连接 GitHub 后，Vercel 可以自动生成分支预览，也会按配置的生产分支处理生产部署。**它不会凭空生成业务测试，也不能默认认为它会等待任意 GitHub Actions 任务结束。** 生产分支可能叫 `main`、`master` 或其他名字，发布前应检查实际配置。参考：[Vercel GitHub 集成](https://vercel.com/docs/git/vercel-for-github)。

“必须测试通过才能合并”需要把实际 CI 任务配置为必需状态检查，并处理管理员绕过、条件跳过等情况。仓库可用功能受 GitHub 计划及可见性影响。参考：[GitHub 受保护分支](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。

需要在 Vercel 的部署阶段接入检查时，可以评估 [Deployment Checks](https://vercel.com/docs/checks)。测试执行器、检查结果和失败时的发布行为都要配置并实际验证，不能把文档中的流程图当成已经工作的自动门禁。

<h2 id="tests">三、上线前究竟测什么</h2>

### 代码与构建检查

农业赋能平台目前的本地入口：

```bash
npm run lint
npm --prefix frontend test
npm test
bash scripts/agent-lint.sh
npm run build
```

这里的 `lint` 是 Vue 类型检查，前端 `test` 是 Node 单元测试，根目录 `test` 是后端 pytest。综合脚本已包含部分检查，日常执行可避免重复；构建和浏览器验收仍应单独确认。

官网的本地入口为 `npm run build`，当前没有 `npm test` 脚本。内容发布应检查文章解析、目录卡片、正文、导航、链接和窄屏可读性；涉及登录、接口或交互的改动，还需增加对应测试。

### Preview 上的业务验收

针对实际变更验证关键路径，例如：

- 登录成功、错误密码提示、登录态与权限限制。
- 产品查询、分类筛选、大屏指标与后端返回一致。
- 图片读取、上传和导出权限。
- 数据为空、加载中、接口超时或失败时，页面给出正确状态。
- 数据采集去重、日期口径、失败重试与日志。

Preview 前端应访问对应 Preview 后端。测试写入使用隔离数据库和测试对象，避免把生产业务数据作为默认测试材料。上线后观察真实数据与日志，验证内容与上线前测试分别记录。

<h2 id="staged">四、生产版本如何先验收再上线</h2>

Preview 与 Production 可以有不同环境变量、接口地址、数据库和鉴权配置。因此预览通过后，还要用生产配置生成生产部署并检查。

Vercel 支持暂存生产部署：构建已经完成，但正式域名暂时继续指向旧版本，验收后再 Promote。通过生产暂存版本验收后，推广该版本无需重新构建。参考：[暂存、推广与回滚](https://vercel.com/docs/deployments/promoting-a-deployment)。

### 控制台方式

1. 进入项目 **Settings → Environments → Production → Branch Tracking**。
2. 关闭 **Auto-assign Custom Production Domains**，让生产构建先暂存。
3. 创建使用 Production 配置的部署，检查部署 URL 和目标提交。
4. 确认正式域名仍在旧版本，对暂存版本执行验收。
5. 将通过验收的生产部署 Promote，随后检查正式域名。

这是逐项目配置。一个项目已采用暂存发布，不代表同账号其他项目也已采用。正式域名的切换由 Vercel 分配部署完成，日常版本发布通常不需要修改 DNS。

### 已授权 CLI 的方式

```bash
# 使用生产配置部署，但暂不分配正式域名
vercel deploy --prod --skip-domain

# 验收上一步返回的部署地址后推广
vercel promote <deployment-url-or-id>
```

使用自定义 CI 和预构建产物时，先拉取 Production 配置，再运行 `vercel build --prod`，随后用 `vercel deploy --prebuilt --prod --skip-domain` 暂存。CI 应固定 CLI 版本，并把凭据保存在 Secrets 中。参考：[Deploy 命令](https://vercel.com/docs/cli/deploy)、[环境变量](https://vercel.com/docs/environment-variables)。

环境变量修改需要新的部署才能生效。验收对象要与最终推广对象一致，不要在验收后临时修改配置并重新构建，却仍沿用旧版本的测试结论。

<h2 id="dependencies">五、前后端、数据库与采集任务</h2>

### 多个部署对象

农业赋能平台有前台、管理后台和 FastAPI 后端。它们可以共享仓库，但分别构建、部署和验收。发布记录应包含各部署 ID 与对应 SHA，核对 API 路由和接口兼容性。

通常先发布向后兼容的新后端，再发布依赖新接口的前端。旧前端仍可能被浏览器缓存，不能只测试最新前后端的组合。多项目切换不能假设是一次原子发布。

### 数据库迁移

优先使用“扩展 → 迁移 → 验证 → 后续移除旧结构”的方式。上线前准备恢复点、兼容策略与权限检查，迁移结果单独记录。

**应用回滚不会撤销数据库迁移，也不会恢复已删除记录或文件。** 新旧代码对数据库结构的兼容性和数据恢复流程必须分别设计。

### Cron 与数据采集

采集代码通过测试、手动试跑成功、真实定时调度成功，是三个不同结果。试跑应验证鉴权、幂等、入库数量、失败处理；首次计划触发后检查任务记录，才能确认自动调度已运行。

Cron 调度与函数资源限制、运行环境规则应另行核查。参考：[Vercel Cron Jobs](https://vercel.com/docs/cron-jobs)。

<h2 id="status">六、目前已具备与仍需配置的内容</h2>

截至本次整理，两个仓库的现状如下：

| 项目 | 已有入口 | 尚不能声称自动完成 |
| --- | --- | --- |
| 农业赋能平台 | 类型、前台单元、后端 pytest、综合检查与构建脚本 | Actions、必需状态检查、自动 E2E 与统一发布门禁 |
| LobsterMaster 官网 | Next.js 构建、Git 部署、内容页面验收 | 独立单元测试套件与完整自动发布门禁 |

当前两个仓库均未包含 GitHub Actions 工作流文件。这篇笔记记录后续发布约定；平台侧的分支保护、Checks 和暂存设置仍应逐项目检查，以实际执行证据为准。

配置自动化之前，由发布执行者按清单完成检查并记录结果。需要自动化时，先把现有检查迁入 CI，再接 Preview 业务测试，最后接暂存生产部署与受控推广，逐阶段验证失败确实会阻断后续步骤。

<h2 id="record">七、发布记录与故障回滚</h2>

每次发布保留：

```text
日期与执行者：
变更范围 / PR / Git SHA：
本地检查命令与结果：
Preview URL、部署 ID 与验收结果：
生产暂存 URL、部署 ID 与配置核查：
正式域名继续服务旧版本的证据：
推广时间、正式域名与冒烟检查：
迁移 / 采集任务结果与未验证项：
可回滚部署、恢复点与兼容性限制：
```

上线故障先定位页面、API、数据源或配置层。代码回滚选上一次已知正常部署；涉及数据或文件恢复则执行独立预案。发布结论应明确已验证的范围，例如“文章已上线并浏览器验收”，不能从“构建成功”推导出“全部业务正常”。

**学习结论：GitHub 管理代码与检查，Vercel 管理部署与流量切换，外部数据库保存状态；把这三个边界连接成有证据的发布流程，才有可重复的上线与恢复能力。**
