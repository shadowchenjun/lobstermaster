## 为什么做一个这么小的 TodoList

极简 TodoList 不是为了解释“我们也能做一个待办应用”。

它更像一个自用工具：打开就能写，写完就能关，最好不要打扰我正在做的事。

很多效率工具一开始都很轻，后来慢慢长出项目、标签、日历、提醒、协作、看板、统计。功能越来越完整，人却越来越不愿意打开。

所以这个小工具反过来做：不追求完整，只追求顺手。

---

## 产品原则

```text
打开即用
  → 输入任务
  → 回车添加
  → 完成勾掉
  → 清空脑子
```

它的原则很简单：

| 原则 | 取舍 |
|------|------|
| 零摩擦录入 | 不注册、不配置，减少进入成本 |
| 单一任务焦点 | 不做复杂项目管理，避免注意力被工具带走 |
| 响应式可用 | 手机、平板、桌面都能随手打开 |
| 团队自用优先 | 不是为了堆功能，而是根据真实使用继续调整 |

---

## 技术选型

| 模块 | 技术 |
|------|------|
| 前端框架 | Next.js |
| 语言 | TypeScript |
| 样式 | Tailwind CSS |
| 部署 | Vercel |

这套栈的好处是路径短：本地写完，推到仓库，Vercel 自动构建，马上能用。

对这种小工具来说，技术架构不应该比工具本身更重。

---

## AIcoding 里的体感

这个工具最适合用 AI 辅助做两类事情：

- 快速搭出第一版交互
- 根据真实使用反馈做细节收敛

比如输入框状态、空列表提示、移动端间距、按钮是否明显，这些事情不难，但很碎。AI 帮我把碎活先铺出来，我再按自己的手感一点点收。

这类小工具的开发节奏应该像打磨一把常用的小刀：不一定锋芒毕露，但每天拿起来都顺手。

---

## 它应该待在 AIcoding，而不是解决方案页

解决方案页更适合放“可复用、可交付、可咨询”的业务方案，比如私有化 Agent 平台、农业赋能平台、云认养系统。

TodoList 更像一篇实践记录：它说明我们怎么用 AI 快速做出自用效率工具，怎么把功能控制在刚刚好，怎么从真实使用里收敛产品形态。

所以把它放进 AIcoding 实践，更符合它的身份。

---

## 小结

极简 TodoList 的价值不在功能多，而在它提醒我一件事：

> 好的效率工具，不是让人更会管理任务，而是让人更快回到任务本身。

有时候，最好的工具就是不抢戏。
