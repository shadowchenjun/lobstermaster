## 背景

社区有个很火的 GitHub 仓库 [Claude Code 最佳实践](https://github.com/shanraisshan/claude-code-best-practice)，Star 数快到三万五千了。里面有个 `development-workflows` 目录，把社区最主流的 10 套工作流全收了——每套拆成 Agent、Command、Skill 三个维度统计对比。

作者花了好几周时间，一套一套装，一套一套跑。最后剩 **5 套值得聊的**。这篇不搞参数横评，只聊实际用的体感。

---

## 一、Everything Claude Code：全家桶

**Star 数**：接近 15 万
**配置量**：近 50 个 agent、80 多个 command、180 多个 skill

全装上的话，Claude Code 基本变成一个微型开发团队。前端、后端、数据库、测试、文档，每个岗位都配了专人。

**问题**：
- 全堆在一起后启动慢得明显
- 上下文里各种 skill 定义互相抢资源
- 每次干活前得先想清楚该调哪个 agent、走哪条命令，思考成本比实际干活还高

**适合谁**：大团队里需要统一工具链的场景。或者你对定制有执念，愿意花大量时间打磨配置。152 个 subagent 的配置都可以直接 copy，省去从零搭建的时间。

**不适合谁**：如果你连 CLAUDE.md 都没写到 60 行，先别碰这个。

**使用建议**：不全装。挑 5-8 个跟你日常工作最相关的 agent 和 skill。其他的留着，哪天需要了再按需加载。

---

## 二、Superpowers：极简规则派

**Star 数**：14 万出头
**配置量**：5 个 agent、3 个 command、14 个 skill

走的是 **TDD-first 路线**，外加一套叫 "Iron Laws" 的硬约束——翻译过来就是：**测试不写完，代码一行都不准动**。

实际用下来最明显的感受：Superpowers 跟 Claude Code 原生功能嵌得很紧，不像外挂，更像原生扩展。尤其是 Plan 阶段的增强——它会强制你检查这块需求在知识库里有没有支撑、上下文还剩多少、拆分粒度合不合理。

**适合谁**：对质量和流程一致性要求高的项目。个人开发者也能用，学习曲线不陡。

**不适合谁**：如果你的开发习惯是"先写代码再补测试"，Superpowers 会让你很痛苦。它在执行阶段会反复提醒你写测试，对敏捷型开发不太友好。

**使用建议**：核心流程（TDD-first 的 Plan → Execute → Review）保留，周边的验证规则可以按项目调整。别把所有 Iron Laws 都打开，选最关键的 3-5 条。

---

## 三、Spec Kit：规格驱动派

**Star 数**：8.7 万
**核心思路**：先写清楚你要什么，再让 AI 动手

流程强制你先出一份详细的规格文档——需求描述、接口定义、数据模型、边界条件、验收标准，一样不能少。文档过关了，才进入代码生成阶段。

作者拿一个分子对接的数据处理管线实测了一下。光规格就磨了一个小时——输入格式、输出字段、精度要求、异常情况处理，全得写清楚。但规格定稿之后，Claude 一次就生成了能通过全部测试的代码——边界条件全覆盖，结构也干净。

对比：同一个管线不写规格直接让 Claude 写，来回改了四版才定型。前面花的那一小时，后面全赚回来了。

**适合谁**：大项目，多模块协作，对代码一致性要求高。或者你本身已经习惯先写设计文档再编码。

**不适合谁**：小项目、原型验证、快速迭代场景。规格写一个小时，原生 Claude Code 十分钟就干完了。

**使用建议**：大模块走 Spec Kit 流程，小功能不用走。找到你的规模分界线。作者的分界线是"如果不需要跟 PM 对齐需求就不写规格"。

---

## 四、gstack：角色扮演派

**Star 数**：近 7 万
**玩法**：让 Claude 扮演不同角色——研究思路设计、算法选型、代码实现、测试验证。不是同时扮，是**分阶段切换**。

官方给这套玩法起了个名字叫 "role personas" 加 "parallel sprints"。

这个跟 Agent Teams 的区别：
- **Agent Teams**：多个 agent 各干各的，并行推进
- **gstack**：同一个 agent 在不同阶段换不同脑子，按顺序模拟一整个研究项目的工作流

跑了一遍完整流程，新鲜是挺新鲜的。但也明显感觉到一个问题：换角色本身也吃上下文。从研究设计切到算法选型再切到代码实现，每换一次都要重新加载角色设定和约束。三轮下来，上下文用掉不少。

**适合谁**：一个人做全栈项目，需要完整的产品思维链。或者你想体验"一个人就是一个团队"的工作方式。

**不适合谁**：如果你本身工作就是在团队里，不需要模拟角色协作。直接让 Claude 写代码就行。

**使用建议**：不要每个任务都走完整角色链。只在需求模糊、需要从零设计的时候启动。就像你不会在改个变量名的时候开研究方案评审会。

---

## 五、原生轻量：什么工作流都不用

这是第五个选项。也是被低估得最厉害的选项。仓库作者自己也在文档里写了：**小任务用原生 Claude Code 就够了，比任何重型工作流都快**。

作者用下来的感受完全一致。上面四套都装过一遍之后，现在 **90% 的时间干脆什么工作流都不开**。改个变量名、修个单行 bug、写个工具函数——一句话扔过去，三分钟之内搞定。复杂任务才上工作流。而且就算上工作流，也只在 Plan 和 Review 阶段使用，执行阶段还是回到原生模式。

> **简单的事情就应该简单做。这是我从过度工程化里学到的最贵的一课。**

---

## 选型速查表

| 场景 | 推荐方案 |
|------|---------|
| 小任务（5 分钟以内） | 原生 Claude Code |
| 个人项目，日常开发 | Superpowers 或原生 |
| 多模块大项目 | Spec Kit + Superpowers |
| 个人全栈开发 | gstack（仅设计阶段） |
| 团队协作 | Everything Claude Code（按需组件） |

---

## 作者的实际工作流（可复制）

- **Plan 阶段**：用 Superpowers 的 Plan Mode 扩展
- **执行阶段**：大部分用原生
- **大模块规格**：用 Spec Kit 的方式写
- **探索阶段**：偶尔开 gstack 的角色模式跑一遍完整逻辑链

选工作流这件事，**选错不算坑。选了之后不敢换，那才是真坑**。

> 这不是标准的、干净的、可推广的工作流。但它是最适合我自己的。

工作流就是个起点。好用的版本都是自己改出来的。
