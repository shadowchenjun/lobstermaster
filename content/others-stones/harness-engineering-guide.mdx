## 什么是 Harness

Harness 是继 OpenClaw 之后的又一个技术热点。它是围绕大模型所做的各种工程化代码的总结，不是固定概念，而是随大模型工程变化而变化。

**核心公式**：

> **Agent = Model + Harness**

- **Model**：负责思考、理解、生成
- **Harness**：负责安排任务流程、上下文管理、工具调用、约束与护栏、反馈闭环、记忆与持续改进等工程化部分

可以把模型想成一个很聪明的人。但这个人再聪明，如果没人给他流程、工具、规则、检查标准，他可能也无法把工作做好。比如：

- 上来就开干，没先看需求
- 做到一半忘了前面说过什么
- 改了代码但没测试
- 明明报错了，还觉得自己差不多做完了
- 第一次犯过的错，第二次还接着犯

**很多时候，问题不是模型"不聪明"，而是它没有一套好的工作机制。这套机制，就是 Harness。**

## Harness 十层架构

### 第 1 层：规则层

> 告诉 Agent 什么能做、什么不能做

规则层是 Agent 必须遵守的最底层、最根本的规则。常见文件形式：

- `AGENTS.md`
- `CLAUDE.md`
- `.cursor/rules`
- `system prompt`
- 项目 README / 团队开发规范

**注意**：`AGENTS.md` 不应该写得太长，它更像目录和总规则，而不是百科全书。具体模块的规则放到对应文档中（如 `docs/api.md`、`docs/database.md`）。

---

### 第 2 层：流程层

> 规定 Agent 先做什么、后做什么

流程层是 Harness 的"工作流"，解决 Agent 容易一上来就开始写代码的问题。

典型编程 Agent 工作流：

```
读需求 → 读规则 → 扫描代码 → 制定计划 → 执行修改
→ 运行测试 → 读取错误 → 修复问题 → 再次验证 → 通过后结束
```

**核心思想**：不要让 Agent 自由发挥，而是让它在一个明确流程中推进任务。

---

### 第 3 层：上下文层

> 决定 Agent 当前应该看到什么

上下文层（Context Engineering）是 Harness 中非常关键的部分。解决的问题：

- 模型上下文窗口有限
- 上下文越乱，模型越容易犯错

**核心原则**：
- 当前需要什么，就给什么
- 当前不需要什么，就不要给
- 长日志只给摘要
- 工具说明和任务文档按需读取

**不是"给模型更多信息"，而是"给模型刚好需要的信息"。**

---

### 第 4 层：工具层

> 让 Agent 能真正动手操作

工具层是 Harness 的"手和脚"。模型本身只能生成文本，但真实工作需要：读文件、写文件、搜索代码、运行测试、打开浏览器、查日志、调接口、提交 Git 等。

**注意**：工具不是越多越好。工具太多会导致：

1. 大量上下文浪费在工具说明上
2. Agent 在工具选择上犹豫，甚至乱用工具

建议先少而精地提供高频工具，再根据真实失败案例逐步增加。

---

### 第 5 层：执行环境层

> 让 Agent 在安全环境（沙箱）里工作

执行环境层给 Agent 准备一个"可干活但不会闯大祸"的工作空间，通常包括：

- 工作目录限制
- 命令白名单
- 文件权限控制
- 网络访问限制
- 超时控制
- 资源限制
- 临时环境 / 沙箱
- 高风险操作人工确认

**核心思想**：让 Agent 在安全边界内做事。

---

### 第 6 层：约束与护栏层

> 把"提醒"变成硬规则

约束层是 Harness 的"刹车"。很多在 prompt 中要求 agent 怎么做的事，agent 并不会百分之百照做，所以更可靠的做法是把要求变成系统里的硬规则。

常见硬约束：

- lint 不过不能完成
- 测试不过不能合并
- 类型检查不过不能通过
- 架构越层依赖直接报错
- 禁止删除测试文件
- 禁止修改生产配置
- 高风险操作必须人工确认

**Harness 重要原则**：能用确定性规则检查的，就不要只靠模型自觉。

---

### 第 7 层：验证层

> 判断 Agent 到底有没有做对

验证层是 Harness 的"质检系统"。Agent 最大的问题之一是：它经常不知道自己有没有做对。

**第一类：自动化测试验证**

```python
import subprocess

def run_pytest():
    result = subprocess.run(["pytest", "-q"], capture_output=True, text=True)
    return {"ok": result.returncode == 0, "output": result.stdout + result.stderr}
```

**第二类：真实行为验证**

前端任务不能只看 HTML 和 CSS，需要用 Playwright 做真实浏览器验证：

```python
def verify_todo_app():
    with sync_playwright() as p:
        browser = p.chromium.launch()
        page = browser.new_page()
        page.goto("http://localhost:3000")
        page.fill("#todo-input", "学习 Harness")
        page.click("#add-button")
        assert page.locator("text=学习 Harness").is_visible()
        browser.close()
        return {"ok": True}
```

**第三类：Evaluator Agent 验证**

让一个独立 Agent 做验证，而不是让 Agent 自己给自己打分。

---

### 第 8 层：记忆与持续改进层

> 让 Agent 不重复犯错

记忆层是 Harness 的"经验系统"，解决 Agent 会反复犯同样错的问题。

**核心思想**：Agent 每犯一次错，就把防止它再次犯错的方法工程化。

流程：Agent 犯错 → 人类诊断原因 → 写入规则 → 加入检查 → 下次自动拦截

**示例**：Agent 经常忘记补测试

1. 把错误写进记忆文件：

```markdown
## 忘记补测试

过去 Agent 修改业务逻辑后，经常忘记补测试。

修复规则：
- 修改业务逻辑时，必须同步补充或更新测试
- 如果没有补测试，必须说明原因
- 验证脚本必须检查 tests/ 目录是否有相关变更
```

2. 在 AGENTS.md 加规则
3. 在 Harness 系统里加入测试检查

---

### 第 9 层：可观测层

> 给 Agent 装"行车记录仪"

可观测层的作用不是让 Agent 更聪明，而是把 Agent 干活的全过程记录下来，方便人类复盘、调试和改进。

**没有可观测层**：只知道"任务失败了"，不知道为什么失败。

**有可观测层**：能看到它读了哪些文件、调用了哪些工具、改了哪些代码、测试有没有跑、失败在哪一步、重试了几次。

**示例日志**：

```json
[
  {"type": "task_start", "task": "新增 /health 接口"},
  {"type": "read_file", "path": "app.py"},
  {"type": "write_file", "path": "app.py"},
  {"type": "run_tests", "command": "pytest -q", "ok": false, "error": "expected 200, got 404"},
  {"type": "fix", "reason": "补充 /health 路由"},
  {"type": "run_tests", "command": "pytest -q", "ok": true}
]
```

---

### 第 10 层：多 Agent 编排层

> 让 Agent 像团队一样协作

多 Agent 编排把复杂任务拆给多个 Agent 分工协作，解决单个 Agent 的问题：

- 上下文太长，容易忘重点
- 既写代码又自查，容易放过自己的错误
- 复杂任务拆不清楚

**常见分工**：

| 角色 | 职责 |
|------|------|
| Planner | 负责拆任务、制定计划 |
| Worker | 负责具体执行 |
| Evaluator | 负责验收结果 |
| Reviewer | 负责检查架构、安全、风险 |

**示例**：做一个 Todo 页面

- **Planner**：规划页面结构、组件拆分、状态管理
- **Worker**：写 React 代码、CSS、交互逻辑
- **Evaluator**：打开浏览器测试新增、删除、完成状态是否可用
- **Reviewer**：检查代码结构、边界情况、是否有安全问题

## 总结

> **模型决定了 Agent 能不能"想"，而 Harness 决定了 Agent 能不能把事情真正"做成"。**

很多人一提到 AI 能力提升，第一反应都是去看模型本身：参数更大了没有，推理更强了没有，代码能力进步了没有。

但当我们真正开始把大模型用在实际任务里时，就会慢慢发现一个问题：**很多时候，瓶颈并不在模型本身，而在模型之外。**

- 它可能理解了需求，却没有按正确流程执行
- 它可能改了代码，却忘了补测试
- 它可能调用了工具，却不知道什么时候该调用
- 它可能输出了"看起来不错"的结果，但实际上并没有真正验证通过

**不是模型不够聪明，而是 Harness 不够完善。**

设计 Harness 系统，才是未来程序员真正要做的事情。
