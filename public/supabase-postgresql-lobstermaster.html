Supabase / PostgreSQL / Backend-as-a-Service

Supabase 到底解决什么问题？

Supabase 不是 PostgreSQL 的替代品，而是围绕 PostgreSQL 组装出来的一套后端开发平台。它把数据库、登录认证、自动 API、文件存储、实时推送、边缘函数和权限策略放到同一个产品里，帮助团队更快搭出可上线的应用后端。

核心结论

PostgreSQL 是数据库引擎；Supabase 是以 PostgreSQL 为核心的云服务和开源后端平台。

Supabase = 托管 PostgreSQL + Auth + 自动 API + Storage + Realtime + Edge Functions + RLS

Definition

Supabase 同时是公司、开源项目和 SaaS 服务。

Supabase Inc.

运营 Supabase 官方产品的公司。你在 supabase.com 创建项目，用的是它提供的官方云服务。

Supabase 开源项目

围绕 PostgreSQL、Auth、Realtime、Storage、API 网关等组件构建的开源后端平台。

Supabase Cloud

官方托管 SaaS。数据库、认证、函数、存储、日志、备份和控制台由 Supabase 官方维护。

第三方托管 Supabase

阿里云、百度云等厂商可以基于开源 Supabase 做自己的托管版本，运行在各自云基础设施上。

Compare

PostgreSQL 是数据库；Supabase 是一套后端服务。

对比项 PostgreSQL Supabase
本质 关系型数据库引擎 以 PostgreSQL 为核心的后端即服务平台
数据能力 SQL、事务、索引、视图、函数、触发器、权限 完整继承 PostgreSQL 能力，并加上控制台、托管、API 和集成服务
用户登录 需要自己实现认证系统 内置 Auth、JWT、Session、OAuth、邮箱验证等
前端 API 通常需要自己写后端接口 可以自动暴露 REST API，也可通过 SDK 直接访问
文件存储 不是核心职责 内置 Storage，适合图片、附件、私有文件和 signed URL
实时能力 可用底层机制实现，但前端接入成本高 内置 Realtime，可订阅表变化、在线状态和广播事件
运维 自建时要自己负责部署、备份、扩容、监控 官方云或第三方云托管，降低运维负担
Capabilities

Supabase 的核心能力可以理解为一组后端积木。

1

Database

托管 PostgreSQL。适合业务数据、复杂查询、事务、索引、扩展和 SQL 权限控制。

2

Auth

用户注册、登录、OAuth、JWT、Session 管理。前端应用不用从零写认证。

3

Auto API

把表和视图自动变成 API。配合 RLS 后，前端可以安全访问授权数据。

4

Storage

存头像、图片、附件、视频、私有文件。可配合权限策略和 signed URL 使用。

5

Realtime

把数据库变化、在线状态或临时事件推送给客户端，减少轮询。

6

Edge Functions

运行后端逻辑，保护 API Key，处理 webhook、AI 调用、支付回调和定时任务入口。

Edge Functions

Edge Functions 是 Supabase 里的轻量后端层。

Edge Functions 适合处理不能放在前端、也不应该塞进数据库函数的逻辑。典型用途包括调用第三方 API、保护密钥、支付 webhook、AI 接口封装、后台任务入口和复杂业务校验。

AI 接口
前端请求 Edge Function，Function 使用服务端密钥调用模型，再返回结果。API Key 不进入浏览器。
支付回调
支付平台回调 Edge Function，Function 验签后用服务端权限更新订单状态。
后台任务
配合 Cron 触发清理、同步、日报、用量统计等系统任务。

和 PostgreSQL Function 的区别

Edge Functions 适合网络请求、第三方服务、webhook、AI、业务 API。
PostgreSQL Function 适合数据库内部计算、触发器、数据校验、聚合和事务内逻辑。
前端 -> Edge Function -> 第三方 API / 数据库 数据库变化 -> PostgreSQL Trigger -> 数据库内部动作
RLS

RLS 是数据库级别的行权限控制。

RLS 是 Row Level Security，中文通常叫行级安全。它控制的不是“用户能不能访问一张表”，而是“用户能访问表里的哪些行”。

在 Supabase 里这很重要，因为前端可能直接通过 SDK 查询表。权限不能只靠前端隐藏按钮，必须落到数据库层。

典型策略

create policy "Users can view own orders" on orders for select to authenticated using ( auth.uid() = user_id );

含义：登录用户只能看到 user_id 等于自己 uid 的订单。

Realtime

Realtime 不是触发器；它负责把变化推送出去。

能力 Realtime Trigger
主要目的 通知客户端数据变了 数据库内部自动执行逻辑
典型用途 聊天、通知、实时看板、协作、在线状态 写审计日志、维护统计字段、校验数据、触发内部处理
运行位置 Realtime 服务和客户端订阅 PostgreSQL 数据库内部
是否主动改库 通常不改，只推送 经常会改
支付 webhook 更新 orders.status = paid Trigger 写入 order_events Realtime 推送 order_events 给前端 用户页面立即显示「支付成功」
Security

Key 可以放 Edge Functions，但 service_role 必须克制使用。

推荐边界

AI、支付、第三方平台的 API Key 放在 Edge Function 的 Secrets 里是正确方向。浏览器用户看不到这些环境变量。

真正的风险不是“Key 放在服务端”，而是 Function 入口没有鉴权、webhook 没有验签、日志泄露密钥，或者滥用 service_role。

service_role 适合什么场景

支付 webhook 验签后更新订单为 paid。

后台任务 清理过期订单、统计用量、生成报表。

管理员操作 封禁用户、审核内容、调整套餐。

跨用户聚合 后台查看全站订单、GMV、用量排行。

Auth Admin 创建/删除用户、修改 app_metadata。

普通用户操作：JWT + RLS 系统后台操作：Edge Function + 鉴权/验签 + service_role 原则：能让 RLS 安全完成的操作，就不要用 service_role。
Decision

怎么选：PostgreSQL、Supabase Cloud、第三方托管或自托管。

只用 PostgreSQL

你已有成熟后端团队，只需要稳定数据库，并希望认证、接口、文件和任务系统都自己掌控。

Supabase Cloud

想最快上线，跟官方文档一致，减少运维，把精力放在产品和业务逻辑上。

国内云托管 Supabase

项目需要国内网络、合规、采购流程或和现有阿里云/百度云资源集成。

自托管 Supabase

团队有运维能力，需要完全控制部署、网络、数据、安全策略和成本结构。

Summary

给技术负责人看的最终判断。

Supabase 的优势

它把应用早期最常见的后端问题打包好了：数据库、登录、权限、文件、实时、函数、控制台。对 MVP、内部系统、AI 应用和中小型 SaaS 很有效。

Supabase 的边界

它不是让你不用懂数据库。真正进入生产后，仍然要认真设计表结构、索引、RLS、审计、备份、成本和权限边界。
