FIELD NOTES / 开发工具选型
RESOURCE-CONSCIOUS DEVELOPMENT · 2026.10.03

让手机成为开发入口先算清资源与维护成本。

官方 App 远程连接，还是云主机上的 cc-connect＋飞书？面向普通开发者、OPC（一人公司）与小研发团队，按实际任务和可用资源做选择。

含双服务器实测容量建议为估算

默认选择：个人先用官方入口；有明确常驻自动化和飞书协作需求，再增加自托管。

“云服务器便宜”不等于“整个方案成本低”。维护时间、任务峰值和恢复成本，常常比桥接程序本身更重要。

01

三类开发者，三种起步方式

01

普通个人开发者

官方入口优先
复用已有开发环境

手机主要用于提需求、查看进度、处理授权和审查改动。已有电脑可常开时用官方远程；电脑经常关机、任务能迁入云环境时，优先官方云任务。

值得自托管的条件：已有闲置且有余量的主机，需要稳定访问自己的环境，并愿意维护机器人和 CLI。

无需为了偶尔在手机上改代码，立即购置常驻服务器或同时订阅两家产品。

02

OPC / 一人公司

开发用官方入口
运营自动化按需接飞书

既做产品，也处理客户和运营。用官方入口完成开发与审查；确有每日巡检、报告、常驻任务时，再把飞书作为轻量任务与通知入口。

值得自托管的条件：常驻工作能持续节省时间，且可复用的脚本、工具和权限边界已经明确。

起步只选一个主智能体；第二个按复杂任务或交叉审查启用，避免无必要的双倍维护。

03

小研发团队

个人开发环境
＋共享飞书任务入口

开发者保留独立工作区和账号。飞书适合接收工单、汇报状态、触发标准任务；执行端应有队列、项目隔离和可追溯记录。

值得自托管的条件：团队经常在飞书协作，有人负责维护，且愿意为执行资源与隔离投入预算。

可从 3–10 人团队场景理解本建议；配置按同时运行的任务数规划，不能按群人数推算。

02

先分清入口和执行位置

A / 官方远程

用手机接管自己的开发环境

Claude：Claude App → Remote Control → 自有主机的 Claude Code
Codex：ChatGPT App → 已配对桌面主机 → 本机或 SSH 项目

优势是任务、授权和结果在官方产品中呈现。任务仍消耗自有主机资源，关机或主机离线会影响远程访问。Claude 可在远端 CLI 开启服务；Codex 当前文档主流程要求 Mac/Windows 桌面主机，再连接 SSH 环境。[1][2]

对现有接入的限制：Claude Remote Control 要求符合条件的订阅登录，不接受 API Key 或自定义 ANTHROPIC_BASE_URL。当前 Sub2API 路径不能直接复用为官方远程。[1]

B / 自托管桥接

用飞书操作常驻 CLI

飞书 App → 飞书机器人 → 云主机 cc-connect
→ Claude Code / Codex CLI → 模型接口与项目工具

服务器保存项目、依赖和智能体环境，适合持续在线。飞书使用长连接接入，无需为消息接收专门开放公网端口；实际项目预览、其他管理服务要另行配置。[5]

边界：cc-connect 是桥接层。它不会自动带来飞书知识库权限、企业级租户隔离或完整桌面端功能；这些需要额外工具、授权和治理。CLI 和适配器版本也需要匹配。[6]

官方入口的另一种执行方式

电脑不能常开？考虑云任务。

Claude Code Cloud 与 Codex Cloud 可从手机使用，任务在厂商云环境中继续执行，不依赖自己的电脑常开。适合能准备好仓库、依赖和权限的任务；本机未提交文件、内网系统和已有登录态不一定直接可用。它解决了自有主机常驻问题，同时引入云环境配置与额度约束。[3] [4]

03

差距更多在工作流程，不能只看模型名称

同一模型、相近配置下，底层生成能力可以接近；实际效果还取决于工具、上下文、权限和接口兼容性。以下是基于官方文档与部署经验的工程判断，非量化性能排名。

窄屏可左右滑动表格，左侧维度保持可见。

主要对比官方远程与自托管；云任务差异在相关项单独标注。能力依据见 [1]–[6]。
维度官方 App 远程 / 云任务cc-connect＋飞书＋自有主机有限资源下的判断
编码与审查适合完整个人开发流程官方 Codex 远程可查看 diff、测试、终端与截图；具体体验以各 App 为准。CLI 执行能力可用读写代码与跑测试由 CLI 承担；飞书长消息不适合逐行审阅大规模变更。复杂改动用官方界面或 Git 平台审查。
便捷性项目与任务呈现更完整；Claude、Codex 分属不同入口。日常聊天中即可派任务；可统一接入多个智能体，但需要配置项目与路由。个人偏官方；飞书重度用户更容易受益。
持续可用性远程依赖主机在线；云任务可在电脑休眠后继续。ECS 可常驻；仍依赖飞书连接、桥接进程、CLI、接口和可用额度。常驻不等于有高可用保障。
资源成本远程复用已有电脑；云任务资源与额度受产品方案约束。需为主机、磁盘、模型调用和维护负责；桥接本身消耗较小。已有服务器必须看可用余量，不能只看规格。
维护成本客户端维护主要由厂商承担；自有执行环境仍需维护。自己排查飞书权限、服务重启、适配变更、密钥、网络、缓存和日志。缺少维护时间时，优先官方入口。
工具与扩展远程可使用主机配置的工具；产品 UI 和能力演进更紧密。可组合脚本、MCP、调度与自选接口；高级能力受 CLI、适配器和版本约束。只有实际用到扩展，才值得承担复杂度。
团队协作适合个人持续开发；团队授权与共享功能视具体方案而定。任务、通知与上下文容易进入工作群；还需补齐执行隔离、队列和审计。聊天会话隔离 ≠ 文件系统隔离。
数据与权限需要管理厂商账号、仓库授权和执行权限。还需管理飞书记录、机器人权限及服务器凭证；自托管 CLI 不等于模型本地推理。两者都需限定项目与工具权限。
成果交付更适合在任务中查看变化和继续迭代；复杂验收仍可回电脑。适合发摘要、附件、PR 链接、预览链接和待办事项。手机端以决策与验收为主，交付物要可追溯。

05

先控制并发，再决定是否买机器

工程规划起点以下不是厂商保证，也不代表实测支持固定人数。总预算应覆盖：常驻业务＋所有同时运行的 CLI、MCP 与工具峰值＋系统余量。

已有条件 / 计划配置建议用途应限制的工作
已有开发电脑个人首选复用；主机常在线时使用官方远程。无法常开且任务可迁入云环境时，用官方云任务。远程不会减少本机构建占用；睡眠、断网、权限弹窗都需考虑。
1–2 GB 小主机轻量桥接、调度或通知节点；完整执行任务放到其他合适环境。不作为 Claude＋Codex 完整开发宿主机；拆分执行端也需额外配置，非即插即用。
独立 2 核 / 4 GB / 40 GB单人轻量起步；一个活跃任务，串行执行。大型构建、多个浏览器、重型 MCP、同机数据库叠加。
独立 4 核 / 8 GB / 80 GB个人 / OPC 的较稳妥规划起点，可安装两种 CLI，按项目实测决定并发。不能据此承诺双重型任务稳定；多仓库缓存和镜像需预算。
4–8 核 / 16 GB 及以上小团队共享执行节点的候选起点，配任务队列、独立工作区和资源限额。3–10 人不意味着 3–10 个并发任务；重构建可交给 CI 或独立 worker。
安装两个客户端 ≠ 同时跑两个任务

可先让 Claude、Codex 交替执行。同一仓库的并行任务使用不同分支 / worktree；避免两个入口同时控制同一个会话或写同一工作目录。

便宜云主机不一定降低总成本

月成本＝账号 / 模型使用＋主机 / 磁盘 / 网络＋维护工时＋故障恢复。飞书入口不会自动减少 token；桥接重试、长会话和额外审查可能增加调用。

账号和额度需单独选择

官方远程、云任务和 CLI 的可用认证方式不完全相同。沿用订阅还是 API 取决于具体产品与模式；订阅也有使用限制，自托管不意味着无限使用。

用自己的项目峰值决定扩容

选一次真实“改动→测试→构建→预览”任务，记录内存、swap、磁盘和耗时。OOM、持续换页或影响既有业务，应先降并发，再优化或扩容。

06

按三个条件，选你的起步方案

这是透明规则驱动的建议器，不使用加权评分，也不请求外部服务。建议基于上文边界，不替代项目容量测试。

建议起步

官方远程＋已有开发电脑

复用已有项目环境，用手机派任务、处理授权和查看结果；先选一个主智能体，无需为偶尔的移动开发新增服务器。

主机需保持在线。Claude 与 Codex 的配对、订阅和 SSH 路径不同，先验证一次完整开发任务。

个人优先减少维护时间。后续有明确飞书自动化需求，再加桥接。
07

把有限资源用在一条能交付的流程上

  1. 选一条主路径个人先验证官方入口；团队先选一个飞书标准任务。使用真实仓库和单个主智能体。
  2. 做一次闭环验收从手机提交需求，执行修改和测试，返回 diff / PR / 预览链接，完成一次人工验收。
  3. 测一次失败恢复验证断线、主机重启、额度耗尽与等待授权时的表现；不要把收到聊天回复当成任务成功。
  4. 再增加并发与角色先增加第二类任务，再增加第二个智能体或用户；每次都检查资源峰值与工作区冲突。

个人 / OPC 的最小交付约定

每次任务返回：改了什么、测试结果、成果链接、还需谁做什么。开发、部署与发布使用清晰的权限范围；需要审查时能在官方界面或 Git 平台接手。

小团队需要补齐的能力

用户到项目的权限映射、独立执行账号 / 工作区、并发队列、凭证隔离、操作记录与负责人。cc-connect 的会话和接入控制能构成基础，不能直接视作完整企业平台。

针对当前杭州与东京：杭州保留单人轻量串行试用；东京维持现有轻量服务。要把个人工具发展为团队长期入口，优先规划独立开发执行主机，避免构建争抢线上网关与数据库资源。
