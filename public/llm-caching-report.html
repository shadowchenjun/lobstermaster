Explicit Caching 与 Implicit Caching
学习汇报

厘清大模型上下文缓存的两种范式：缓存的究竟是什么、Cache Key 从哪来、为什么还要调用 LLM、以及在 RAG 场景下如何组合使用以同时降低 Token 成本并保持回答质量。

汇报日期：2026-10-02
主题：LLM 推理优化
01 / 核心概念

一句话区分两种缓存

Explicit Caching（显式缓存）：由调用方主动指定 Cache Key，把固定长上下文的 KV 向量预存起来，跨请求复用。
Implicit Caching（隐式缓存）：由平台自动比对完整请求内容，发现完全相同的请求时自动复用结果，调用方零感知。

Explicit Caching 显式缓存

  • 控制方：调用方（业务代码）
  • 缓存对象：固定长上下文的 KV 注意力张量
  • 触发方式：手动传入 cache_key
  • 典型场景：长 System Prompt、固定知识库文档
  • 优点：精准可控，可跨会话复用
  • 缺点：需要业务层维护 Key 和版本

Implicit Caching 隐式缓存

  • 控制方：LLM 平台自动处理
  • 缓存对象：完整请求的推理结果
  • 触发方式：自动识别重复请求，无需 Key
  • 典型场景：测试脚本重复调用、用户重复提问
  • 优点：零代码改造，开箱即用
  • 缺点：匹配严格（差一个字符就失效），无法主动管理

通俗类比

显式缓存：你把一本厚厚的说明书起名叫 book_001 交给平台存好。之后每次提问，带上名字 book_001，平台直接复用这份文档，不用每次重新上传整本。

隐式缓存：你每次完整复制粘贴一整段提问，平台看到一模一样的文字，悄悄记住答案；你再次粘贴完全相同内容，直接返回上次答案。只要改一个字，就失效。

02 / Cache Key 机制

调用方如何知道 Cache Key？

核心结论：Explicit Caching 的 Cache Key 是调用方自己定义、自己保管的，不是平台自动返回的。少数平台（如 Gemini）由平台创建缓存后返回资源 ID，但调用方同样必须把这个 ID 持久化保存。

两种主流 API 范式

范式一：调用方自定义字符串 Key（OpenAI / AWS Bedrock / Azure）

  • 开发者自行命名，如 system_prompt_v2、kb_contract_2026，保证业务内唯一即可
  • 首次请求带上 Key + 完整长上下文，平台将该上下文绑定到 Key 上，创建缓存
  • 后续请求复用同一个 Key，平台自动加载预存的 KV
  • 调用方需在本地数据库 / Redis / 配置中维护「Key → 缓存内容版本」映射

范式二：平台生成资源 ID（Gemini / 部分 Anthropic 风格接口）

  • 发起 create cache 接口提交待缓存内容
  • 平台创建成功后返回一个 cache 资源 ID（即 Cache Key）
  • 调用方必须将返回的 ID 保存到数据库或 Redis
  • 后续推理请求传入该 ID 以复用缓存
踩坑提醒：平台不会帮你记住你创建过哪些 Cache Key。如果调用方代码丢失了这个 Key 字符串，缓存条目将无法再访问，只能重建。此外，Key 只是路由标记，不是加密凭证。

如何确认缓存命中？

不是靠返回 Key，而是看 response 中的 usage 字段：

  • cached_tokens > 0 或 cache_read_input_tokens > 0：缓存命中
  • cache_creation_input_tokens > 0：刚刚新建缓存
Key 命名建议：带上版本号，如 kb:product-manual-v3。一旦缓存内容更新（系统提示词改版、知识库文档更新），必须更换全新 Key，否则会读到旧缓存。
03 / 核心原理

缓存了输入，为什么还要调用 LLM？

这是最容易混淆的一点。Explicit Caching 缓存的不是最终回答，而是输入上下文的 KV（Key-Value）注意力张量。它跳过的是「重复编码长上下文」这一步，但「基于上下文生成新答案」这一步仍然要走模型。

被缓存 vs 仍需执行的部分

被缓存、跳过的部分

  • 超长 System Prompt
  • 前置参考文档 / 知识库片段
  • 这一大段固定文本的 Token 编码和 Attention 计算
  • 对应 KV 向量预存，后续直接加载

每次仍需执行的部分

  • 用户本次新 Query（动态输入，需编码）
  • 自回归生成输出 Token（模型实时推理）
  • 采样（temperature、top_p）带来的随机性

KV 缓存 vs 上游业务结果缓存

维度 LLM Explicit KV Cache 上游业务缓存（Redis 问答缓存）
缓存内容 输入上下文的 KV 注意力张量 完整输入 → 完整输出问答对
命中时是否跑模型 仍然跑（只省了上下文编码） 完全不跑，直接返回旧答案
用户 Query 可变吗 可以，每次不同 Query 都能复用 KV 不行，Query 必须完全一致才命中
输出是否固定 不固定，每次实时生成（有随机性） 固定，原样返回上次结果
谁维护 LLM 平台 业务代码

输出随机性问题

KV 缓存只优化输入侧，不约束生成侧的输出随机性。只要 temperature > 0，即使完全相同的缓存上下文 + 完全相同的用户 Query，多次调用返回的输出文本也可能有差异。

如果业务强要求相同输入得到相同输出，必须：

  • 设置 temperature = 0 并固定 seed 参数（大幅降低随机，但非 100% 保证）
  • 或在业务层叠加 Redis 结果缓存（命中时直接返回，完全不走模型）
认知误区：开了 Explicit Caching 不等于相同请求返回相同回答。它解决的是「长上下文重复编码的成本」，不是「多次调用输出稳定」。
04 / 实战实例

RAG 场景：Explicit Caching + 动态 Query

这正是 Explicit Caching 最核心的使用场景：固定的知识库文档只编码一次，后续不同用户提问复用这份 KV，同时模型基于缓存上下文 + 当前 Query 实时生成答案。

场景设定

  • 静态固定内容：一份产品手册（约 80k tokens，长期不变），绑定 cache_key = "kb:product_manual_v1"
  • 动态输入：用户每次不同提问（保修期多久？怎么退换货？支持哪些支付方式？）
  • 目标：产品手册只编码一次，后续所有不同提问复用 KV，节省大量输入 Token 费用

步骤一：首次调用 — 创建缓存

第一次请求完整传入长文档，平台构建 KV 缓存：

POST /v1/messages — 首次创建缓存 
// 请求体
{
  "model": "claude-3-5-sonnet",
  "cache_control": {
    "type": "ephemeral",
    "cache_key": "kb:product_manual_v1"
  },
  "messages": [
    {
      "role": "system",
      "content": "你是产品客服，只能基于下面【产品手册】回答用户问题。
【产品手册】：{这里放80k token完整产品文档文本}"
    },
    {
      "role": "user",
      "content": "保修期多久？"
    }
  ],
  "max_tokens": 1024
}

// 返回 usage（cache_creation_input_tokens > 0 表示缓存创建成功）
{
  "usage": {
    "cache_creation_input_tokens": 80000,
    "cache_read_input_tokens": 0,
    "input_tokens": 8010,
    "output_tokens": 156
  }
}

步骤二：后续调用 — 同 Key 不同 Query

不再重复上传 80k 产品手册，只传当前用户问题，带上同一个 Cache Key：

POST /v1/messages — 复用缓存，换 Query 
{
  "model": "claude-3-5-sonnet",
  "cache_control": {
    "type": "ephemeral",
    "cache_key": "kb:product_manual_v1"  // 同一个 Key
  },
  "messages": [
    {
      "role": "system",
      "content": "你是产品客服，只能基于手册回答。",
      "cache_control": {"type": "cached"}  // 标记走缓存
    },
    {
      "role": "user",
      "content": "怎么申请退换货？"  // 每次换新 Query
    }
  ],
  "max_tokens": 1024
}

// 返回 usage（cache_read_input_tokens > 0 表示命中缓存）
{
  "usage": {
    "cache_creation_input_tokens": 0,
    "cache_read_input_tokens": 80000,  // 读取缓存，低价计费
    "input_tokens": 42,               // 只有本次 Query
    "output_tokens": 210
  }
}

请求流程图

用户 Query 每次不同的问题
→
带上 cache_key kb:product_manual_v1
→
LLM 加载 KV 复用 80k 手册向量
→

Python 伪代码

rag_with_explicit_cache.py 
import requests

CACHE_KEY = "kb:product_manual_v1"
LONG_KNOWLEDGE_DOC = open("product_manual.txt", "r").read()

def llm_rag_query(user_question, create_cache=False):
    messages = []
    if create_cache:
        # 首次：传入完整文档，创建缓存
        messages.append({"role": "system",
            "content": f"基于手册回答：\n{LONG_KNOWLEDGE_DOC}"})
    else:
        # 复用缓存：system 段标记为 cached，不再传全文
        messages.append({"role": "system",
            "content": "基于手册回答问题",
            "cache_control": {"type": "cached"}})
    messages.append({"role": "user", "content": user_question})

    return requests.post("https://api.anthropic.com/v1/messages",
        json={"model": "claude-3-5-sonnet",
              "cache_control": {"type": "ephemeral",
                                 "cache_key": CACHE_KEY},
              "messages": messages, "max_tokens": 1024}).json()

# 1. 首次调用，创建缓存
llm_rag_query("保修期多久？", create_cache=True)
# 2. 后续调用，不同 Query，复用缓存
llm_rag_query("怎么申请退换货？")
llm_rag_query("支持哪些支付方式？")
注意：Explicit Caching 适合「参考文档固定不变」的 RAG（整本手册、长合同）。如果是分片 RAG —— 每次检索出来不同 chunk —— 上下文一直在变，无法命中 KV 缓存，不适合此方案。
05 / 工程实践

组合策略与最佳实践

三层缓存组合架构

生产环境中最常用的方案是把三种缓存叠加使用，兼顾成本、延迟和输出一致性：

第一层：Redis 结果缓存 完全相同 Query 直接返回，不调用 LLM
→
第二层：Explicit KV Cache 固定长上下文复用，省 Token 编码费
→
第三层：模型实时生成 结合缓存 KV + 当前 Query 生成答案

选型决策表

业务场景 推荐方案 原因
长固定 System Prompt / 知识库 Explicit Caching 固定上下文只编码一次，大幅省 Token
FAQ 固定问答，要求答案一字不差 Redis 结果缓存 + Explicit KV 命中结果缓存直接返回；未命中时 KV 省成本
测试脚本 / 批量重复调用 Implicit Caching 零代码改造，平台自动复用
RAG 分片检索（每次 chunk 不同） 不适合 Explicit，可加 Redis 结果缓存 上下文前缀一直在变，无法命中 KV
需要可复现的评测结果 temp=0 + 固定 seed + 结果缓存 单靠 KV 缓存不能保证输出一致

踩坑清单

  • Key 版本管理：缓存内容更新后必须换新 Key，否则读到旧数据
  • TTL 过期：显式缓存通常有 5~60 分钟的存活时间，超时后自动失效，下次请求会重建
  • 内容不可变：同一个 Key 绑定的内容不能变，内容变了即使 Key 不变也会缓存失效
  • 输出不稳定性：KV 缓存不锁死输出，temp > 0 时同 Query 也会有措辞差异
  • 匹配严格度：Implicit Caching 要求完整请求完全一致，差一个字符就 miss
  • Key 持久化：平台不会帮你记 Key，业务侧必须自行存储 Key 与内容版本的映射
总结：Explicit Caching 优化的是「长上下文重复编码」的成本，Implicit Caching 优化的是「完全重复请求」的成本，而业务层 Redis 结果缓存解决的是「输出一致性」的问题。三者定位不同，生产环境中通常组合使用。
