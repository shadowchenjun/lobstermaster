01

为什么这个项目必须做 Eval

当前桥接服务已经打通企业微信回调、RAGFlow 调用、合规过滤、线索识别和 SQLite 留痕。下一阶段的核心问题不再是“能不能回复”，而是“回复是否稳定、是否像招商客服、是否能合规推进线索”。

业务质量

高频问题要稳定

加盟流程、费用、利润、材料、供应链、门头、运营等问题需要持续回归，避免 prompt 或规则改动后答偏。

合规红线

高风险问题必须收口

收益承诺、区域保护、合同付款、授权真假必须进入人工确认，不能让模型自行发挥。

线索运营

客服回答要能推进下一步

回答不是只给知识点，还要自然引导城市、门店情况、联系方式，并沉淀到客户和线索表。

02

这里的 Eval 到底评什么

对招商加盟客服来说，eval 不是找一个标准答案逐字对齐，而是用样本、评分器和回归记录持续判断 AI 是否完成业务目标，并守住风险边界。

评测对象

层级当前项目对应内容
意图识别classify_intent 是否把问题路由到正确策略。
标准话术standard_answer、profit_answer、generic_fallback_answer 是否覆盖关键事实。
合规改写rewrite_for_compliance 是否拦截“保证回本、稳赚、保底收益”。
去 AI 味humanize_answer 是否去掉 Markdown、chunk_id、Fig、知识库口吻。
完整链路后续扩展到 FastAPI + RAGFlow + polish + 发送前最终文本。

评测重点

  • 不承诺固定收益、稳赚、保证回本。
  • 城市开放、区域保护、授权、合同付款必须建议人工确认。
  • RAGFlow 未命中或异常时不能把英文 not found 发给客户。
  • 不输出“根据知识库”“综合来看”“以下是”等报告腔。
  • 不输出 chunk_id、Fig、ID、Markdown 等检索痕迹。
  • 高意向客户要被引导提供城市、门店情况或联系方式。
03

选型逻辑：为什么先用 Promptfoo

评测工具很多，但当前项目最需要的是本地可跑、可进 CI、能写业务断言、能快速沉淀回归集。Promptfoo 正好适合第一阶段；Braintrust、LangSmith、HoneyHive 更适合中后期的实验管理、人工质检和生产闭环。

工具 定位 在本项目中的角色 采用时机
Promptfoo 开源 CLI / CI 评测框架 本地回归测试、规则断言、红队样本、Prompt/RAG 改动前后对比。 现在采用
Braintrust Eval-first 平台 管理实验、数据集、人工审核、生产样本回流，适合多人协作和持续质量闭环。 当 eval case 超过数百条、需要多人标注时引入。
LangSmith Trace + Dataset + Experiment 如果后续采用 LangChain / LangGraph agent，可用于调试 agent step、tool call、dataset experiment。 当客服链路升级为复杂 agent 时评估。
HoneyHive Agent observability + online eval 适合复杂 agent、工具调用、RAG pipeline 的生产追踪和在线评分。 当线上失败链路变复杂、需要 OTel 级追踪时评估。
Langfuse 开源 LLM observability 记录生产 trace、成本、prompt 版本、在线评分，可自托管。 当需要生产观测与 prompt 管理时引入。
Helicone AI Gateway + 请求观测 适合多模型网关、成本、缓存、限流和请求日志。 当模型网关治理成为重点时评估。
Datadog LLM Observability 企业 APM + LLM 观测 统一纳入企业级日志、APM、安全和告警。 当团队已经重度使用 Datadog 时评估。
结论 第一阶段采用 Promptfoo 是因为它最轻、最贴近工程回归、最容易与现有 Python 规则层和 JSONL 数据集结合。中后期再按“实验管理、生产追踪、人工质检、企业治理”的实际痛点引入 Braintrust、Langfuse 或 Datadog。

05

数据集设计：按招商业务意图和风险分层

种子数据集不追求标准答案逐字一致，而是约束业务事实、风险红线和下一步动作。后续应从真实对话持续补充差样本。

分层 当前意图 样例 评测重点
低风险直答 online_status、knowledge_status 你是挂了吗？知识库更新了吗？ 直接回复，不调用 RAGFlow，不输出知识库痕迹。
高频招商问题 join_process、fee、materials、storefront 怎么加盟？加盟费多少？需要哪些资料？门头有什么要求？ 覆盖流程、费用、材料、门头等关键事实，引导补充城市和门店情况。
利润与收益 profit 利润怎么样，多久能回本？这个项目赚钱吗？ 必须表达不承诺固定收益，不能出现稳赚、保证回本、保底收益。
必须人工确认 city_policy、contract_payment 这个城市能做吗？合同怎么签，打款到哪里？怎么证明授权？ 必须建议招商顾问确认，不自动承诺区域、合同、收款、授权。
模糊追问 unknown 你们这个到底行不行？ 自然追问具体关注点，避免编造结论或机械兜底。

指标体系：把客服质量变成可观察数字

招商客服的评测指标要把普通质量、合规风险和线索推进分开看。高风险问题不能被整体平均分掩盖。

离线评测指标

意图准确率、必须包含项命中率、禁用词违规率、转人工召回率、微信文本卫生、Prompt/RAG 修改前后回归差异。

线上观测指标

RAGFlow 命中率、fallback 占比、ragflow_exception、ragflow_not_found、重复回复率、高意向线索沉淀率、人工接管率。

07

三阶段实施路线

不建议一开始就上重平台。先用 Promptfoo 建立本地回归标准，再接完整 RAGFlow 链路，最后把真实生产数据纳入在线观测和人工质检。

阶段 1 · 已落地

本地策略层回归

用 Promptfoo + Python provider 测本地规则、标准话术、合规改写和去 AI 味。当前 20 条种子用例通过。

阶段 2 · 下一步

完整链路 Eval

新增本地 only 的 /eval/answer endpoint，让 Promptfoo 直接打 FastAPI + RAGFlow + polish 的最终回复。

阶段 3 · 生产闭环

线上观测与人工质检

从 SQLite 导出真实问答，优先复盘 fallback、not_found、高风险和高意向样本，沉淀为回归集。

08

最佳实践：让 Eval 真正有用

Eval 的价值不在于一次性证明 AI 永远正确，而在于每次改规则、prompt、知识库和 RAG 参数时，都能及时发现退步。

实践 项目落地方式 注意点
硬规则优先 用 must_not_include 和 Python assertion 拦截收益承诺、付款风险、知识库痕迹。 软质量不能抵消合规失败。
高风险单独看 risk_level 分为 low、medium、high、critical。 critical 必须 100% 通过。
数据集从真实对话长出来 scripts/export_eval_pairs.py 导出真实问答。 优先补充 fallback、not_found、高意向和转人工失败样本。
本地策略层与完整链路分开测 当前 Promptfoo 测本地策略层，后续 HTTP provider 测完整链路。 本地通过不等于 RAGFlow 检索一定正确。
发布前跑回归 npm run test + npm run eval:local。 Prompt、知识库、意图规则、polish prompt 改动后都要跑。
